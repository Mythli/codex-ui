# Coder Architecture

This app is intentionally shaped like an onion around Codex. Codex is the center of the system: it owns the thread protocol, work execution, thread storage, model behavior, and most backend semantics. Coder should mostly bridge Codex into a browser UI, then reduce Codex traffic into state that is easy to render.

## North Star

- Treat Codex as the product backend. Avoid recreating Codex behavior in the Coder API layer.
- Keep the server thin. Server code should connect transports, manage app sessions, expose assets to the browser, and run protocol middleware that cannot safely run in the browser.
- Keep UI meaning in the frontend reducers/selectors. Incoming requests, responses, and events are reduced into sidebar state, transcript state, and render blocks.
- Prefer generated Codex types over local copies. Only add local protocol helpers where they normalize wire traffic or project it into UI-friendly shapes.

## Codex Types

The Codex app-server protocol types are generated, not authored by hand:

- `apps/coder/types/generated/app-server`
- `apps/coder/types/generated/app-server/v2`

They are generated by the app package script:

```sh
pnpm --filter @taylordb/coder generate:protocol-types
```

The app should usually import through the local wrapper instead of reaching into individual generated files:

- `apps/coder/types/appServer.ts` aliases generated request, notification, thread, turn, model, config, and filesystem types.
- `apps/coder/protocol/requests.ts`, `responses.ts`, `events.ts`, `traffic.ts`, `thread-items.ts`, and `wire.ts` define the app's parsed protocol surface around those generated types.
- `apps/coder/types/index.ts` re-exports the public app types, protocol types, transport types, and reducer state types.

Do not edit files under `apps/coder/types/generated/app-server` manually.

## Core Surface

The old broad connection bucket is split into three import surfaces:

- `@coder/types` / `apps/coder/types`: shared public app types, generated app-server aliases, transport interfaces, and feature state types.
- `@coder/protocol` / `apps/coder/protocol`: protocol parsing, packet normalization, traffic envelopes, and thread-item helpers built around generated Codex types.
- `@coder/client` / `apps/coder/client`: browser request helper and Socket.IO transport for sending generated protocol methods.

The React `apps/coder/app/features/connection` feature is intentionally narrower: socket status, bounded diagnostics, and `codexTrafficReceived` ingestion. It should not own generated types, parsing, or the protocol client.

## Onion Layers

1. Codex app-server and generated protocol types.
2. Shared app types in `apps/coder/types` and protocol parsing in `apps/coder/protocol`.
3. Browser protocol client in `apps/coder/client`.
4. Server-side bridge code in `apps/coder/backend`, `apps/coder/middlewares`, `apps/coder/assets`, `apps/coder/appSocket.ts`, and `apps/coder/dependencies.ts`.
5. Browser Redux traffic ingestion through `codexTrafficReceived`.
6. Reducers that project traffic into renderable UI state.
7. React components that render the already-reduced state.

The important boundary is between layers 3 and 4. The backend can adapt protocol traffic for browser constraints, but the frontend owns product state.

## Request Flow

The common request path looks like this:

```text
UI thunk
  -> requestCodex()
  -> CodexSocketIoTransport
  -> Socket.IO /codex namespace
  -> AppCodexSessionRegistry
  -> LiveCodexBackendProvider
  -> managed AppServerClient or socket-backed Codex backend
  -> Codex app-server
```

Key files:

- `apps/coder/client/codexClient.ts` wraps requests. It dispatches request, response, and response-error traffic to Redux using the same `CodexProtocolTraffic` envelope the rest of the app consumes.
- `apps/coder/client/codexTransport.ts` creates the browser Socket.IO transport for `/codex`.
- `apps/coder/client/CodexSocketIoTransport.ts` sends browser requests to the app socket and emits backend traffic to listeners.
- `apps/coder/backend/socketNamespace.ts` owns the `/codex` Socket.IO namespace, session registry, request timeouts, and traffic forwarding.
- `apps/coder/backend/backendProvider.ts` creates either a managed Codex app-server process or a socket-backed Codex transport.
- `apps/coder/backend/AppServerClient.ts` speaks to `codex app-server --listen stdio://` and parses the Codex wire stream.
- `apps/coder/dependencies.ts` is the main composition root for env, assets, middleware, backend provider, session registry, and Socket.IO server creation.

On the browser side, `apps/coder/app/store/provider.tsx` binds the transport to Redux by listening for transport traffic and dispatching `codexTrafficReceived`.

## Backend Middleware

The protocol middleware stack is server-side only today. It is not Redux middleware and it is not shared with the browser.

Key files:

- `apps/coder/backend/middlewareTransport.ts`
- `apps/coder/middlewares/types.ts`
- `apps/coder/middlewares/createCodexProtocolMiddlewareStack.ts`
- `apps/coder/middlewares/createLocalFileReadMiddleware.ts`
- `apps/coder/middlewares/markdown-rewrite/createMarkdownRewriteMiddleware.ts`
- `apps/coder/middlewares/createTrafficMeasurementMiddleware.ts`

The stack currently does three things:

- Reads local `.jsonl` session files directly for `fs/readFile` when that path is local and browser hydration needs it.
- Rewrites Markdown image URLs and local file links into `/codex-assets/...` URLs so browser-rendered transcripts can display files Codex referenced from disk or data URLs.
- Measures request, response, and traffic timing for diagnostics.

The browser-asset bridge is the most product-visible part of this stack:

- `apps/coder/assets/createAssetHelper.ts` registers file, byte, and data-URL assets and serves them under `/codex-assets`.
- `apps/coder/middlewares/markdown-rewrite/handlers/image-urls.ts` rewrites Markdown image nodes.
- `apps/coder/middlewares/markdown-rewrite/handlers/local-file-links.ts` rewrites local link and definition nodes.
- `apps/coder/middlewares/markdown-rewrite/protocol-rewrite.ts` applies those rewrites across thread reads, turn starts, live events, rollout JSONL, and user input.

Keep this middleware focused on bridge concerns. New product state or UI interpretation should normally live in reducers/selectors, not in backend middleware.

## Traffic Reduction

The frontend design is: emit or receive Codex protocol traffic, then reduce it into UI-friendly state.

The shared traffic action is:

- `apps/coder/app/features/connection/state/codexTrafficActions.ts`

The main Redux composition is:

- `apps/coder/app/store/rootReducer.ts`
- `apps/coder/app/store/configureStore.ts`

Major state areas:

- `threadIndex`: sidebar-facing thread/project index.
- `threads`: loaded per-thread transcript/session state.
- `chatListMeta`: UI-only unread and hydration metadata.
- `selection`: current draft or selected thread.
- `composer`: prompt, attachments, selected model, reasoning effort, and permission mode.
- `modelsConfig`: model/config responses from Codex.
- `codexConnection`: socket status and bounded diagnostics.

## Thread Index Reducer

The sidebar index is reduced through:

- `apps/coder/app/features/threads/state/threadIndexSlice.ts`
- `apps/coder/app/features/threads/state/threadIndexReducer/CodexThreadIndexReducer.ts`

`CodexThreadIndexReducer` consumes list requests/responses, thread lifecycle events, turn lifecycle events, name updates, archive/unarchive events, and optimistic `turn/start` request traffic. It produces:

- `threadsById`
- `threadOrder`
- `projectsByCwd`
- `projectOrder`
- `threadIdsByTurnId`
- loading/error/activity state

This reducer should stay sidebar-oriented. It should not grow full transcript responsibilities.

## Thread Reducer

The full selected-thread state is reduced through:

- `apps/coder/app/features/thread/state/loadedThreadsSlice.ts`
- `apps/coder/app/features/thread/state/threadReducer/CodexThreadReducer.ts`
- `apps/coder/app/features/thread/state/threadReducer/internal/hydrationStrategies.ts`
- `apps/coder/app/features/thread/state/threadReducer/internal/eventStrategies.ts`
- `apps/coder/app/features/thread/state/threadReducer/internal/renderBlocks.ts`

`loadedThreadsSlice` owns the collection of loaded threads, active thread id, provisional-thread promotion, and request/turn/session correlation maps. Each thread delegates protocol traffic to `CodexThreadReducer`.

`CodexThreadReducer` owns the per-thread lifecycle:

- request tracking
- thread read/start/resume hydration
- local rollout JSONL hydration
- live event application
- session metadata
- token usage and model reroute metadata
- transcript state
- render-block projection

`renderBlocks.ts` is the composed projection from normalized transcript state to the blocks consumed by the transcript UI. The UI should receive render blocks that are already grouped and labeled enough to render without needing to reinterpret raw Codex traffic.

## Optimistic State

Optimistic submission exists, but it is fragile and should be treated as technical debt.

Current behavior lives mostly in:

- `apps/coder/app/features/composer/state/turnThunks.ts`
- `apps/coder/app/features/thread/state/loadedThreadsSlice.ts`
- `apps/coder/app/features/connection/state/trafficRouting.ts`
- `apps/coder/app/features/thread/state/threadReducer/CodexThreadReducer.ts`
- `apps/coder/app/features/threads/state/threadIndexReducer/CodexThreadIndexReducer.ts`

When sending from a draft, the app creates a `local-thread:*` provisional thread, dispatches an optimistic `turn/start`, calls `thread/start`, promotes the provisional thread to the real thread id, then sends the real `turn/start` while reusing metadata. Existing-thread sends also dispatch optimistic `turn/start`, then resume and start the real turn.

This gives useful UI responsiveness, but correctness depends on request ordering, metadata correlation, provisional id promotion, and duplicate suppression. The README tracks this as outstanding work:

- `README.md` section "Refactor optimistic thread and turn handling"
- `README.md` section "Replace custom optimistic traffic with Codex-native events"
- `README.md` section "Split the large thread reducers into understandable units"

Future work should make optimistic traffic a deliberate state machine with tests, not scattered correlation logic.

## Click E2E Tests

The click tests are the app-level confidence suite for Coder. We rely on them to understand whether the Codex bridge, reducers, route hydration, transcript rendering, sidebar behavior, attachments, asset rewriting, and live interaction loop still work together.

They are intentionally higher level than reducer tests. A passing click suite does not prove every reducer edge case, but it does prove the main browser workflows still hold when real UI, Socket.IO transport, Codex backend traffic, Redux reduction, and React rendering are composed.

Key files:

- `apps/coder/e2e/click/run-click-e2e.mjs`
- `apps/coder/e2e/click/playwright.config.ts`
- `apps/coder/e2e/click/support/ClickAppPage.ts`
- `apps/coder/e2e/click/*.spec.ts`

The normal command is:

```sh
pnpm test:e2e:click
```

The runner executes the spec files serially, prunes old run directories, and writes artifacts under `apps/coder/test-results/click/<run-id>`. Playwright is configured for one Chromium worker, retained failure traces, screenshots on failure, and video for every test. Many tests also attach explicit full-page screenshots and JSON diagnostics through `ClickAppPage`.

`ClickAppPage` is the shared test harness. It opens the live app, waits for the shell and backend model list, drives the thread sidebar, sends prompts, uploads files, checks transcript state, verifies scroll behavior, records screenshots, and uses direct `/codex` Socket.IO requests for setup/inspection such as `thread/list`, `thread/start`, and `model/list`.

### Current Coverage

`asset-markdown.spec.ts`

- `writes byte assets once by hash and serves cache and file urls`: protects the asset helper. It proves byte assets are content-addressed, repeated writes reuse the same cache file, local file paths become opaque `/codex-assets/file/...` URLs, cache/file assets can be served over HTTP, and missing files return 404. This exists because browser transcript rendering cannot safely use raw local paths.
- `resolves local targets and rewrites only markdown asset urls`: protects Markdown rewriting rules. It proves relative paths, absolute paths, and `file://` URLs are normalized to the same browser-safe asset URL, data images are cached, existing `/codex-assets` URLs are left alone, and web/mail/anchor links are not rewritten. This exists to keep the backend bridge narrow and predictable.
- `rewrites streamed assistant markdown deltas`: protects live event rewriting. It proves an `item/agentMessage/delta` event containing a local file link is rewritten to `/codex-assets/file/...` without leaking `file://` or the raw path. This exists because live streaming traffic and hydrated thread reads must behave consistently.

`ssr-initial-hydration.spec.ts`

- `redirects root to latest thread with transcript, menu state, and composer data`: proves `/` redirects to the latest real thread and hydrates a usable workspace with transcript, selected sidebar row, model menu state, reasoning control, composer, and no app error. This exists to catch SSR/initial-data regressions before they look like an empty app.
- `loads and reloads a direct thread route with transcript, project, and composer data`: proves `/chats/:id` opens directly, reloads cleanly, keeps the route thread selected, expands the active project row, and hydrates the same workspace controls. This exists because direct links and browser reloads are core navigation paths.

`live-chat-activity.spec.ts`

- `sends live messages and persists attached images after reload`: exercises the main live thread loop. It selects a Codex model, creates a new thread, sends a first prompt, verifies optimistic user-message visibility and running work visibility, checks selection stability, checks no unexpected loader appears, verifies transcript auto-scroll and manual-scroll preservation, reloads and compares transcript signatures, sends a shell-work prompt, uploads text and image attachments, verifies rendered image assets, verifies a local file link is rewritten and fetchable through `/codex-assets`, sends an image-only message, reloads again, and confirms no duplicate user messages. This exists because it covers the hardest composition path: optimistic state, live Codex traffic, asset bridging, attachment rendering, scroll behavior, hydration, and duplicate suppression.

`work-timeline.spec.ts`

- `streams grouped command work and keeps it expandable after completion`: proves command tool calls stream into a running work block, grouped command summaries collapse and expand, command rows stay collapsed until opened, the completed work block keeps the same id, reload preserves the completed timeline, and command details remain expandable. This exists to protect the `renderBlocks.ts` projection and the transcript work timeline UI.
- `completes file work without leaving an in-progress file loader`: proves file edits finish as completed file-change cards rather than stuck progress rows. It asks Codex to create one file, waits for final text, checks no running/in-progress file entries remain, verifies one file-change card with the expected filename and line stats, and reloads to compare transcript state. This exists because file work passes through several reducer/render states and can otherwise leave stale loading UI.

`sidebar-status.spec.ts`

- `shows running and unread status for a background sleep turn`: creates one ready thread, starts a long-running prompt in another thread, switches away, verifies the sleeping thread shows running state in the thread sidebar, then verifies it becomes unread when it finishes, clears unread when opened, and stays read when switching away again. This exists to protect sidebar activity/unread state across background turns.

`latest-threads.spec.ts`

- `opens latest real threads top-down`: reads backend thread order, reads visible switcher order, then opens each visible real thread in order and expects a ready transcript with no app error. It records screenshots and click-order JSON. This exists to catch regressions in sidebar ordering, row clickability, route changes, and lazy thread hydration across real thread history.
- `switches between two real threads repeatedly with relaxed readiness`: repeatedly alternates between two visible threads and waits for each to become ready. This exists to catch route/selection/hydration regressions that only appear after repeated navigation.
- `switches between two already opened threads within cached readiness budget`: opens two threads, then requires later switches to render within the cached readiness budget. This exists to protect the loaded-thread cache path and prevent already-opened chats from flashing loading or empty states.

### How To Use Them

Run the click suite after changes that touch the Codex transport, backend middleware, asset helper, Redux traffic routing, reducers, transcript rendering, thread sidebar, composer submission, attachments, SSR hydration, or routing.

When a click test fails, inspect the generated video, screenshot, trace, and attached JSON before changing code. These tests are meant to explain what the user actually saw: whether a row was clickable, whether a transcript was empty, whether a loader appeared, whether scroll jumped, or whether live and reloaded transcript state diverged.

Click tests should stay focused on user-visible workflows and cross-layer integration. Add reducer/unit tests for narrow state-machine behavior, then use click tests to protect the workflows that prove the app still works as a browser product.

## Practical Rules For New Work

- Start from the generated Codex type and method name. If Codex has a request/event/response shape, use it.
- Put transport and browser-bridge adaptations in the backend bridge.
- Put product state reduction in Redux reducers or selectors.
- Keep the backend middleware stack server-side unless there is an intentional shared-runtime design.
- Keep the thread index reducer about lists, projects, ordering, and activity.
- Keep full transcript behavior in the thread reducer and render-block projection.
- Add characterization tests before splitting the large reducers, especially around optimistic sends, hydration, sidebar ordering, and live event application.
